# 澄清请求-前端流程

- Agent 发起 `clarify.requested`（“澄清请求”）
```json
[
    "clarify.requested",
    {
        "event": "clarify.requested",
        "run_id": "f9a01712049c4d838d306310622438f4",
        "clarify_id": "14f86a9b6852457d953d28e8d1115e82",
        "question": "你上一条消息「tett 12」想表达什么？这是一个测试，还是有什么具体需求？",
        "choices": [
            "测试澄清功能（我确实在测试）",
            "是笔误，我想问别的事情",
            "我想测试某个 Hermes 功能，稍后告诉你",
            "其他"
        ],
        "timeout_ms": 300000,
        "session_id": "msr5tpxeqcnl39"
    },
    "P_vvFmS"
]
```

---

- `Chat store` 提取数据并保存到：
  - `pendingClarifies`：所有会话的待“澄清请求”
    ```json
    {
        "key": "msr5tpxeqcnl39",
        "value": {
            "sessionId": "msr5tpxeqcnl39",
            "clarifyId": "7a51b72a19c64a66bf07e7adeb19ceee",
            "question": "测试：请问你现在能看到这条澄清请求吗？如果能看到，请选择一个选项或直接回复。如果你看不到，选「没收到通知」，我来排查通知配置。",
            "choices": [
                "收到了！我点击了这个选项",
                "没收到通知",
                "换个问题再试一次",
                "其他"
            ],
            "timeoutMs": 300000,
            "requestedAt": 1786607339839
        }
    }
    ```
  - `activePendingClarify（计算属性）`：当前会话的待“澄清请求”
    ```json
    {
        "sessionId": "msr5tpxeqcnl39",
        "clarifyId": "14f86a9b6852457d953d28e8d1115e82",
        "question": "你上一条消息「tett 12」想表达什么？这是一个测试，还是有什么具体需求？",
        "choices": [
            "测试澄清功能（我确实在测试）",
            "是笔误，我想问别的事情",
            "我想测试某个 Hermes 功能，稍后告诉你",
            "其他"
        ],
        "timeoutMs": 300000,
        "requestedAt": 1786603961391
    }
    ```


---

- `MessageList` 根据 `activePendingClarify` 是否有值，弹出 “澄清请求”面板
    - 如果 `activePendingClarify.choices`
      - 有数据：则使用此数据依次显示按钮 + “忽略”按钮 
      - 没有数据：则显示输入框 + “回复”按钮
    - 点击按钮：触发“响应澄清” 并关闭 “澄清请求”面板
    - “忽略”：正常触发“响应澄清”，只是请求体中的 `response` 字段为空字符串

---

- `Chat store` “响应澄清请求”
  - 发起“响应澄清”网络请求
    ```json
    [
        "clarify.respond",
        {
            "session_id": "msr5tpxeqcnl39",
            "clarify_id": "14f86a9b6852457d953d28e8d1115e82",
            "response": "测试澄清功能（我确实在测试）"
        }
    ]
    ```
    - 从 `pendingClarifies` 中删除此待“澄清请求”

---

- Agent 回复“澄清解决”
```json
[
  "clarify.resolved",
  {
    "event": "clarify.resolved",
    "clarify_id": "14f86a9b6852457d953d28e8d1115e82",
    "resolved": false,
    "session_id": "msr5tpxeqcnl39"
  },
  "P_vw_1H"
]
```
---

- `Chat store` 清除待澄清状态

---

- 超时
  - 前端未触发“响应澄清”前，一直显示（没有超时计时和超时状态）
  - 超时由后端计时，有可能在下一次对话内容中给出超时提示

# 问 Hermes

## *Question 1:* `Hermes 的澄清机制（或流程）是什么样的？`
## *Answer:*

---

我已经把完整链路都查清楚了。下面从工具定义 → 三条平台的执行路径 → 你观察到的测试现象，讲清楚 Hermes 的澄清机制：

---

## 1. 工具层：`clarify` 工具的定义

源码：`hermes-agent/tools/clarify_tool.py`

- **参数**：`question`（必填）+ `choices`（可选，**最多 4 个**，超出会被截断）
- **两种模式**：
  - 多选模式：给 4 个选项，UI **自动追加第 5 个「Other (type your answer)」**
  - 开放模式：不传 `choices`，纯自由文本回答
- **返回**：JSON 字符串 `{question, choices_offered, user_response}`
- **本质**：薄分发器——自身不做 UI，把交互委托给平台注入的 `callback(question, choices)`。拿不到 callback 就返回 `{"error": "Clarify tool is not available in this execution context."}`

## 2. 平台层：三种执行路径

| 平台 | 实现 | 交互方式 | 超时 |
|------|------|----------|------|
| **CLI** | `cli.py` | 同步 `input()`，方向键选择 | 默认 **120s**（`CLI_CONFIG["clarify"]["timeout"]`），超时自动放弃让 agent 自行决定 |
| **Gateway**（Telegram 等） | `tools/clarify_gateway.py` | 按钮 UI（内联键盘）或编号列表文本回退 | `agent.clarify_timeout`，**默认 600s**，超时返回 `[user did not respond within 10m]` |
| **Web UI**（本项目） | Socket.IO 桥接 | 输入卡片 + 选项按钮 + 文本框 | 桥接层传递 `timeout_ms`（测试观察到 5 分钟） |

### Gateway 的核心机制（事件队列 + 线程阻塞）

`tools/clarify_gateway.py` 是整个机制最精巧的部分：

```
agent 线程                                  事件循环 / UI 线程
─────────                                  ─────────────────
register() 创建 entry {clarify_id, question, choices}
    │
    ▼
wait_for_response() 阻塞在 threading.Event 上
    │   （每 1 秒醒来一次，保持心跳存活，防止
    │     inactivity watchdog 把 agent 杀掉）
    │                                         用户点击按钮 / 输入文本
    │                                         resolve_gateway_clarify(clarify_id, response)
    │                                         entry.event.set()
    ▼
拿到 response，返回给 agent 继续执行
```

关键设计：
- **`clarify_id`** 全局唯一，按钮回调和文本拦截都靠它定位条目
- **按 session 索引**（FIFO），下一个自由文本消息会被捕获为答案（`get_pending_for_session` 只认 `awaiting_text=True` 的条目）
- **会话边界清理**：`/new`、网关关闭、agent 被驱逐时调用 `clear_session()`，把 `response` 置为 `""` 并 set 事件——所以空响应可以区分「用户没答」和「会话被中断」
- **1 秒轮询**防止线程永久挂死（注释里明确写了：直接 `Event.wait(600)` 会把 inactivity watchdog 坑死）

## 3. Web UI 路径（hermes-web-ui）完整链路

```
Python Agent（bridge 池内运行）
    │  调用 clarify 工具，callback 被桥接
    ▼
Agent Bridge 发出 clarify.requested 事件
    │  {clarify_id, question, choices, timeout_ms}
    ▼
服务端 handle-bridge-run.ts 转发
    │  replaceState(sessionMap, ...) + emit('clarify.requested')
    ▼
Vue 客户端 globalClarifyRequestedHandler
    │  存入 pendingClarifies（按 sessionId + clarifyId 索引）
    ▼
UI 渲染澄清卡片
    │  "The agent has a question for you" + 选项按钮 + 输入框 + Reply/Dismiss
    ▼
用户点按钮 / 输入 / Dismiss
    │  socket.emit('clarify.respond', {session_id, clarify_id, response})
    ▼
服务端转发 bridge clarify_respond
    │  → Python 侧 resolve → agent 线程解除阻塞
    ▼
桥接回发 clarify.resolved
    │  清理前端 pendingClarifies 卡片
```

对应前端代码：`client/src/api/hermes/chat.ts`（`globalClarifyRequestedHandler`、`respondClarify`）、`client/src/stores/hermes/chat.ts`（`pendingClarifies`）、i18n 里有 `clarifyTitle/clarifyPlaceholder/clarifyDismiss` 等文案。

## 4. 回看你的测试数据

| 次数 | 现象 | 机制解释 |
|------|------|----------|
| 1–3 | `[user did not respond within 5m]` | 超时路径：桥接层 5 分钟没等到响应，返回哨兵字符串，agent 线程解除阻塞 |
| 4、6 | 收到选项文本 | 正常路径：`clarify.respond` → `resolve_gateway_clarify` → 事件 set |
| 5 | `""` 空字符串 | 边界情况：可能是点了 **Dismiss** 或会话清理，`response` 被置为空串后 set 事件 |

**设计意图**：不管用户答不答、答什么，agent 线程都**永远不会永久卡死**——超时/放弃/Dismiss 都有明确出口，这正是「阻塞式交互」在异步网关架构里安全运行的关键。

## *Question 2:* `模型（LLM）在对话过程是怎么告诉 Hermes 要触发“澄清请求”的？`
## *Answer:*

---
机制核实清楚了。核心答案一句话：**LLM 不是用自然语言「告诉」Hermes 的，而是通过标准的函数调用（function calling）协议，在它的 API 响应里返回一个结构化的工具调用**。Hermes 的 agent 循环解析后分发到 clarify 处理器。

---

## 完整机制：LLM → Hermes 的五步链路

### 第 1 步：模型「看到」工具定义

对话开始时，Hermes 会把 `clarify` 的函数 schema 注入模型的工具列表。模型看到的是这样的定义（`CLARIFY_SCHEMA`）：

```json
{
  "name": "clarify",
  "description": "Ask the user a question when you need clarification, feedback, or a decision before proceeding...",
  "parameters": {
    "type": "object",
    "properties": {
      "question": { "type": "string", "description": "The question to present to the user." },
      "choices": { "type": "array", "items": {"type": "string"}, "maxItems": 4 }
    }
  }
}
```

### 第 2 步：模型「决定」并输出结构化工具调用

当模型判断需要澄清时，它的补全响应**不是**返回文字，而是返回 `tool_calls` 字段——一段标准的 OpenAI 风格 JSON：

```json
{
  "role": "assistant",
  "content": null,
  "tool_calls": [
    {
      "id": "call_abc123",
      "type": "function",
      "function": {
        "name": "clarify",
        "arguments": "{\"question\": \"你上一条消息「tett 12」想表达什么？\", \"choices\": [\"测试澄清功能\", \"是笔误\"]}"
      }
    }
  ]
}
```

这就是 LLM「告诉」Hermes 的全部——**参数以 JSON 字符串形式塞在 `function.arguments` 里**。

### 第 3 步：Hermes 解析并分发

agent 循环读取这条 assistant 消息，解析出 `function_name="clarify"`、解析 `arguments` JSON 得到 `function_args`，然后走分发器（`agent_runtime_helpers.py:1679`）：

```python
elif function_name == "clarify":
    from tools.clarify_tool import clarify_tool as _clarify_tool
    return _clarify_tool(
        question=function_args.get("question", ""),
        choices=function_args.get("choices"),
        callback=agent.clarify_callback,   # ← 平台注入的回调
    )
```

### 第 4 步：回调把请求送到你面前

`agent.clarify_callback` 是启动时由平台注入的（CLI / gateway / Web UI 桥接各有各的实现）。在 Web UI 里它触发 `clarify.requested` 事件 → 前端弹出澄清卡片。**agent 线程在此期间阻塞等待**。

### 第 5 步：用户回复变成工具结果，回到对话流

你的回复通过 `clarify.respond` 传回，回调返回字符串，`clarify_tool` 包装成 JSON：

```json
{"question": "...", "choices_offered": [...], "user_response": "第 6 次，收到 ✅"}
```

这个结果作为 `tool` 消息（带 `tool_call_id`）追加进对话历史，模型在同一轮内继续——看到工具结果后，它可能继续调用其他工具、或者给出最终回答。

## 一张图总结

```
┌──────────┐  ① 注入 schema（tools 列表里有 clarify）
│  LLM 模型 │◄─────────────────────────────┐
└────┬─────┘                              │ ⑤ tool 结果回到对话流
     │ ② 响应里返回 tool_calls:            │    模型继续执行
     │    {name:"clarify", arguments:"..."}│
     ▼                                    │
┌─────────────────────┐  ③ ④ ┌──────────────────────┐
│ Hermes agent 循环    │─────►│ clarify_tool 分发器    │
│ 解析 tool_calls      │      │ callback=平台回调       │
└─────────────────────┘      └──────────┬───────────┘
                                        │ 阻塞等待用户输入
                                        ▼
                              澄清卡片 / 按钮 / 输入框
                                        │ 用户回复
                                        ▼
                              resolve → 返回 response 字符串
```

**所以「触发」的本质**：模型输出一个 `tool_calls` 条目 = 它对 Hermes 说"请执行 clarify"；Hermes 只负责解析、分发、注入 UI、等待回复、把结果还给模型。整个机制对模型来说和调用 `read_file`、`terminal` 没有任何区别——它甚至不知道用户界面长什么样。

---

顺带一提：你之前测试里观察到的「5 分钟超时」哨兵字符串 `[user did not respond within 5m]`，也是通过同一条链路回到模型的——模型看到这个 tool 结果后，会自行决定"用户没答，我按默认继续"。
