# 审批请求-前端流程

- Agent 发起 `approval.requested`（审批请求）
```json
[
    "approval.requested",
    {
        "event": "approval.requested",
        "run_id": "deece3254cde40b09bc93619def3b55f",
        "approval_id": "ea2861f5c05a4bf8b867dc12877a9712",
        "command": "rm -rf test-1 && echo \"DELETED OK\" && ls -la",
        "description": "recursive delete",
        "choices": [
            "once",
            "session",
            "always",
            "deny"
        ],
        "allow_permanent": true,
        "timeout_ms": 300000,
        "session_id": "msrazadlug0708"
    },
    "P_-2k73.0"
]
```

---

- `Chat store` 提取数据并保存到：
  - `pendingApprovals`：所有会话的待“审批请求”
    ```json
    {
        "key": "msrazadlug0708",
        "value": {
            "sessionId": "msrazadlug0708",
            "approvalId": "ea2861f5c05a4bf8b867dc12877a9712",
            "command": "rm -rf test-1 && echo \"DELETED OK\" && ls -la",
            "description": "recursive delete",
            "choices": [
                "once",
                "session",
                "always",
                "deny"
            ],
            "allowPermanent": true,
            "isMemoryWrite": false,
            "requestedAt": 1786673553910
        }
    }
    ```
  - `activePendingApproval`：当前会话的待“审批请求”
    ```json
    {
        "sessionId": "msrazadlug0708",
        "approvalId": "ea2861f5c05a4bf8b867dc12877a9712",
        "command": "rm -rf test-1 && echo \"DELETED OK\" && ls -la",
        "description": "recursive delete",
        "choices": [
            "once",
            "session",
            "always",
            "deny"
        ],
        "allowPermanent": true,
        "isMemoryWrite": false,
        "requestedAt": 1786673553910
    }
    ```

---

- `MessageList` 根据 `activePendingApproval` 是否有值，弹出 “审批请求”面板
    - 根据 `activePendingApproval.isMemoryWrite`，显示：“内存写入”按钮
    - 否则根据 `activePendingApproval.choices`，排列组合显示：“单次允许”、“会话内允许”、“始终允许”、“拒绝” 按钮
    - 点击按钮：触发 “响应审批请求” 并关闭 “审批请求”面板

---

- `Chat store` “响应审批请求”
  - 发起“响应审批请求”网络请求
    ```json
    [
        "approval.respond",
        {
            "session_id": "msrazadlug0708",
            "approval_id": "ea2861f5c05a4bf8b867dc12877a9712",
            "choice": "once"
        }
    ]
    ```
    - 从 `pendingApprovals` 中删除此待“审批请求”

---

- Agent 回复“审批解决”
```json
[
    "approval.resolved",
    {
        "event": "approval.resolved",
        "approval_id": "ea2861f5c05a4bf8b867dc12877a9712",
        "choice": "once",
        "resolved": false,
        "session_id": "msrazadlug0708"
    },
    "P_-8Sdj"
]
```
---

- `Chat store` 清除待审批状态

---

- 超时
  - 前端未触发“响应审批”前，一直显示（没有超时计时和超时状态）
  - 超时由后端计时，有可能在下一次对话内容中给出超时提示

# 问 Hermes

## *Question:* `Hermes 的审批机制（或流程）是什么样的？`
## *Answer:* 

---

结合你的实际配置（`config.yaml`）和源码（`tools/approval.py`、`gateway/platforms/api_server.py`），Hermes 的审批机制如下：

## 1. 触发条件（什么命令需要审批）

`tools/approval.py` 里有一组 `DANGEROUS_PATTERNS` 正则，命中即触发审批，分两类：

| 类别 | 示例 | 说明 |
|------|------|------|
| 递归/根路径删除 | `rm -rf x`、`rm /` | 你今天测试的就是这条 |
| 敏感文件写入 | `~/.ssh/*`、`.env`、`config.yaml`、`~/.bashrc` 等 | 含 shell 展开形式（`$HOME/.ssh`） |
| 系统配置路径 | `/etc/`、`/private/etc/`（macOS） | |
| 不可恢复破坏 | `mkfs`、`dd` 写块设备、shutdown/reboot | 这类连 `--yolo` 都不能放行 |
| 代价高但可恢复 | `git reset --hard`、`chmod -R 777`、`curl xxx \| sh` | yolo 可以放行 |

## 2. 审批模式（`approvals.mode`）

| 模式 | 行为 |
|------|------|
| `manual` | **总是弹审批**（你当前配置，默认值） |
| `smart` | 用辅助 LLM 自动判断：低风险自动放行，高风险才弹窗 |
| `off` | 跳过所有审批（等同 `--yolo`） |

## 3. 完整流程（以你今天测试为例）

```
你发消息 → 我调 terminal 执行 rm -rf test-1
  → detect_dangerous_command() 命中 "recursive delete"
  → 按 session_key 创建 pending 审批（FIFO 队列，可 /approve all）
  → 发送审批事件 → API Server（POST /v1/runs/{run_id}/approval / SSE 推送）
  → Web UI 弹出审批卡片（批准/拒绝）
  → 等待 approvals.timeout 秒
     ├─ 批准 → 命令执行
     ├─ 拒绝 → 命令不执行，我收到拒绝结果
     └─ 超时 → BLOCKED（你看到的 "Command timed out without user response"）
```

## 4. 你机器上的实际配置

```yaml
approvals:
  mode: manual        # 总是弹审批
  timeout: 60         # 等 60 秒，超时即拒绝
  cron_mode: deny     # 定时任务命中危险命令 → 直接拒绝，不弹窗（防止无人值守卡死）
  mcp_reload_confirm: true
  destructive_slash_confirm: true
```

所以之前两次 `rm -rf` 都超时，是因为 **60 秒内 Web UI 上没有响应**——这正是 API Server 的 `_run_approval_sessions`（run_id ↔ session_key 映射）和 `asyncio.Queue` 等待机制的表现：超时后等待方收到空结果 → 判定为未同意 → BLOCKED。

## 5. 相关机制

- **`command_allowlist`**（config.yaml，当前为空）：加入白名单的命令永久免审批
- **YOLO 模式**：`--yolo` 或 `HERMES_YOLO_MODE=1`；注意它在**模块导入时冻结**，会话中途改环境变量无效（防提示注入绕过）
- **Cron 特殊处理**：定时任务通过 `HERMES_CRON_SESSION` 标记，永远走 `cron_mode`（默认 deny），不会挂起等待
- **插件钩子**：`pre_approval_request` / `post_approval_response` 可扩展审批前后行为
